## Context

README "Limitations" says the library does not check that values or codes are unique, and that lookups return whichever instance is found first. Since the lookup refactor (commit b6a9a34), `Lookup<TVnum>` fills three dictionaries with `TryAdd` (`src/VnumEnumeration/Vnum.cs`, around line 297 after BUG-0001), so every duplicate is already detected at build time and then silently dropped.

Probe on 2026-10-26: a type with `A = new(1, "a")` and `B = new(1, "b")` reports two instances from `GetAll` while `FromValue(1)` returns `A`; `B` can never be found by value and JSON `1` always deserializes to `A`.

A duplicate value or code is always an authoring mistake. Silent first-wins turns it into a wrong-answer bug at some distant call site. Consumers currently have to copy the checks from `tests/VnumEnumeration.Tests/Helpers/VnumTestingHelper.cs` into their own test suites to catch it.

## Scope

1. In the `Lookup<TVnum>` constructor, throw `InvalidOperationException` on a duplicate `Value` or a duplicate `Code` (ordinal), naming the type, the clashing value or code, and both members' codes. The exception surfaces on the first lookup for the type, where discovery already runs.
2. Decide what to do with codes that differ only by case (`"Abc"` and `"ABC"`): they are distinct under ordinal comparison but make `FromCode(ignoreCase: true)` ambiguous. Options: throw at build (strict), or document that case-insensitive lookup requires case-unique codes and throw only from the ignore-case path.
3. Partial tables built during static initialization (see BUG-0001) contain a subset of the instances, so they cannot produce false duplicates; keep it that way.
4. Replace the README "No duplicate validation" limitation with the new rule and add a row to the "Errors" table. Keep the test helper's checks; they still cover enum coverage.

`breaking: true`: a consumer type that relied on first-wins now throws on first use.

## Decision points

- Case-insensitive duplicates: strict at build, or only when an ignore-case lookup is made.
- Whether to add a public `Vnum.Validate<TVnum>()` that forces discovery, for consumers who want a one-line test per type. `GetAll<TVnum>()` already does this, so probably not.

## Acceptance criteria

- [ ] Duplicate `Value` throws on first lookup with a message naming the type, the value and both codes
- [ ] Duplicate `Code` (exact) throws with the same shape of message
- [ ] The case-insensitive decision is implemented and tested
- [ ] Deliberately broken sample types in `TestData.cs` and tests in `VnumDiscoveryTests`
- [ ] README "Limitations", "Behavior" and "Errors" updated
- [ ] `dotnet build VnumEnumeration.slnx` and the full test suite pass
