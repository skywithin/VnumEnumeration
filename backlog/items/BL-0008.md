## Context

The package targets `net10.0` only. On 2026-10-26 the source compiled unchanged for `net8.0` (`dotnet restore -p:TargetFramework=net8.0` then `dotnet build`): every API used (`Unsafe.As`, `ReferenceEqualityComparer`, `ArgumentNullException.ThrowIfNull`, `Volatile`, `System.Text.Json` converters) exists in .NET 8. Consumers on the .NET 8 LTS cannot install the package today for no technical reason.

## Scope

- `src/VnumEnumeration/VnumEnumeration.csproj`: `<TargetFrameworks>net8.0;net10.0</TargetFrameworks>` (net9.0 is STS; skip unless wanted).
- `tests/VnumEnumeration.Tests/VnumEnumeration.Tests.csproj`: multi-target too, so the suite runs on both.
- Workflows (`.github/workflows/build-and-publish.yml`, `pre-release-publish.yml`): `actions/setup-dotnet` currently installs `10.0.x` only. Building `net8.0` needs only the reference pack from NuGet, but running the tests on `net8.0` needs the 8.x runtime: add `8.0.x` to `dotnet-version`.
- README "Supported frameworks" and the `PackageReference` example; the CLAUDE.md "Project" line.
- `Cache<TVnum>.IsStaticInitializerRunning` in `Vnum.cs` already has a `#if NET9_0_OR_GREATER` branch (`DiagnosticMethodInfo`, added by BL-0003) and a `GetMethod` fallback for older targets; confirm the fallback compiles and that the reentrant-lookup test passes on net8.0.

## Resolution (2026-10-26)

The library and the test project now target `net8.0;net10.0`, and both workflows install the `8.0.x` and `10.0.x` SDKs so CI can run the net8.0 tests. The CI steps themselves needed no change: build, test and pack already work per project and handle multiple targets.

One source change was needed, contrary to the item's expectation of none. The .NET 8 trimming analyzer reports `VnumJsonConverterFactory.CreateConverter`'s `MakeGenericType` call as IL2070, where .NET 10 reports the same call as IL2071. Because BL-0003 made IL codes build errors, the net8.0 build failed until IL2070 was suppressed alongside IL2071, with the same justification. The parameter cannot carry the annotation instead, because it belongs to the overridden base method.

The net8.0 build compiles the `GetMethod` fallback BL-0003 left in `Cache<TVnum>.IsStaticInitializerRunning`. The reentrant-lookup and null-field tests pass on net8.0, so the fallback is exercised.

Decisions:
- net9.0 not targeted: .NET 9 apps use the net8.0 build.
- The README `PackageReference Version="10.*"` example was left alone. It refers to the package version, not the target framework.

Not decided here: the package major version has mirrored the .NET version since the "Upgrade .net10" commit (1.2.0 to 10.0.0). A package numbered 10.x now supports .NET 8, which is fine. But the pending breaking release needs a new major under semantic versioning, and 11.0.0 would read as ".NET 11". The user chose not to file an item for this yet.

Verification: Debug and Release builds of both targets with zero IL warnings; 132/132 tests on net8.0 and on net10.0; `dotnet pack --no-build -p:Version=10.2.0-local` produced a package with `lib/net8.0` and `lib/net10.0`.
