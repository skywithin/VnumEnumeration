## Context

`Vnum<TEnum>(long value, string code)` sets `Id = LongToEnum(value)`, which only checks that the value fits the enum's underlying integral type. A value that is not a declared member is accepted. Probe on 2026-10-26: with `enum ByteId : byte { One = 1 }`, `new ByteVnum(7, "x")` constructs and reports `Id == (ByteId)7`.

The test helper's `All_Vnum_Instances_Must_Have_Matching_Enum` exists to catch this in consumers' test suites. The library can enforce it at construction, which for the normal `public static readonly` usage means at static initialization, so the mistake surfaces the first time the type is touched rather than in whichever test suite remembered to check.

The `TEnum` constructor is not affected: callers pass a member, and a cast to an undefined value is their deliberate choice.

## Scope

- After `LongToEnum`, check `Enum.IsDefined<TEnum>(Id)` and throw `ArgumentOutOfRangeException` (the type the constructor already uses for range errors) naming the enum and the value.
- `[Flags]` enums: combined values are not "defined". Skip the check when `TEnum` carries `FlagsAttribute`, and say so in the README.
- README "Errors" table: add the case.

`breaking: true`: a value accepted today throws at static initialization.

## Acceptance criteria

- [x] Constructing from an undefined value throws `ArgumentOutOfRangeException` with the enum name and value in the message; the existing out-of-range tests still pass (and now also pin their original message)
- [x] A `[Flags]` sample enum with a combined value still constructs (test)
- [x] README "Errors" and "Enum-backed Vnum" updated
- [x] `dotnet build VnumEnumeration.slnx` and the full test suite pass (132/132)

## Resolution (2026-10-26)

The `Vnum<TEnum>(long, string)` constructor now calls `Enum.IsDefined` after the existing range conversion and throws `ArgumentOutOfRangeException` (param name `value`, actual value attached) with the message `Value 7 is not a defined member of enum ByteId.` The range check still runs first, so out-of-range values keep their original message; the out-of-range theory now asserts that. The `TEnum` constructor is unchanged.

`[Flags]` enums skip the check, as the item proposed: whether `TEnum` carries `FlagsAttribute` is read once into a static field. Validating each set bit against the declared flags was considered and not done.

Tests: `ByteVnum.Create(7)` throws with the new message; `FlagsVnum.Create(3)` (a new `[Flags]` sample, `PermissionId : byte`) constructs with `Id == Read | Write`. The undefined-member test was confirmed to fail against the previous constructor. Both new calls are trim-safe; the build, which treats IL warnings as errors, reports none.

Docs: README "Errors" row and a paragraph under "Enum-backed Vnum"; one clause on the CLAUDE.md `Vnum<TEnum>` bullet.

Breaking: a value accepted before now throws at static initialization (wrapped in `TypeInitializationException`). Ships in the next major version with BL-0001 and the other `breaking: true` items.
